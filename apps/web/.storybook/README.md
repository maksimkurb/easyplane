# Storybook (apps/web)

Every UI component and page renders from typed fixtures with **no backend**.
Storybook runs against the app's real `vite.config.ts` (Tailwind 4, `@/` alias,
React plugin), so styles and imports behave exactly like `bun run web:dev`.

```bash
bun run storybook              # from the repo root → dev server on :6006
bun run --cwd apps/web storybook
bun run storybook:build        # static output in apps/web/storybook-static

# preview the static build without a backend
bunx http-server apps/web/storybook-static -p 6011 -c-1
```

## Configuration

| File | Purpose |
| --- | --- |
| `.storybook/main.ts` | Vite builder, story glob, a11y + docs addons, `public/` static dir (logo + MSW worker) |
| `.storybook/preview.tsx` | global decorators, toolbar globals, viewports, MSW loader |
| `.storybook/fixtures/` | typed fixture data (devices, networks, access policy, topology, …) |
| `.storybook/mocks/handlers.ts` | MSW handlers for every API endpoint the components call |
| `public/mockServiceWorker.js` | MSW service worker (generated by `bunx msw init public --save`; committed) |

The build output (`apps/web/storybook-static`) is gitignored.

> Storybook is pinned at 9.1.21 as requested. Its `@storybook/react-vite`
> package lists `vite ^5 || ^6 || ^7` as a peer while the app is on Vite 8;
> both `storybook dev` and `storybook build` work with the app's config here.
> Revisit the pin when Storybook 10 tooling is chosen.

### Toolbar

- **Theme** – Light / Dark. Applied through the real `ThemeProvider`, which adds
  `.light` / `.dark` to `<html>` exactly like the app.
- **Language** – English / Русский. Applied through the real `LanguageProvider`
  and the shared i18next instance (`src/i18n`).
- **Viewport** – Desktop 1440, Tablet 768, Phone 390 (plus the built-in
  presets).

Every story runs inside the same provider stack as `main.tsx`:

```
ThemeProvider → LanguageProvider → QueryClientProvider (retry: false)
  → TooltipProvider → AuthProvider → wouter Router (memory location)
```

`AuthProvider` is included so `useAuth()` works; `/api/auth/me` and
`/api/config` come from MSW fixtures (`owner@example.com`, admin).

### Router and pages

The Router uses `wouter/memory-location`. Set the path per story with
`parameters.location` (and `parameters.search` for `?addDevice=1`):

```tsx
export default {
  title: "Pages/DeviceDetail",
  component: DeviceDetailPage,
  parameters: { layout: "fullscreen", location: "/devices/dev-nas-01" },
  render: () => (
    <AppShell>
      <Route component={DeviceDetailPage} path="/devices/:id" />
    </AppShell>
  ),
} satisfies Meta<typeof DeviceDetailPage>
```

Pages that read `useParams()` (device detail) must be mounted through a
`<Route>`; pages that take a `networkId` prop get it from story args. Use
`layout: "fullscreen"` for app frames so the decorator does not add padding.

## Adding a story

1. Put the file next to the component: `src/components/device/device-row.stories.tsx`.
2. Use CSF3 with the generated types and arg controls:

```tsx
import type { Meta, StoryObj } from "@storybook/react-vite"
import { DeviceRow } from "@/components/device/device-row"

const meta = {
  title: "Components/Device/DeviceRow",
  component: DeviceRow,
  args: { device: homeDevices[0]!, networkId: "net-home-lab" },
  argTypes: { credentialsMode: { control: "boolean" } },
} satisfies Meta<typeof DeviceRow>

export default meta
type Story = StoryObj<typeof meta>

export const OnlineHubAnchor: Story = {}
```

3. Import fixtures from `.storybook/fixtures/*` (relative path: components are
   three levels below `apps/web`, so `../../../.storybook/fixtures/devices`).
4. `preview.tsx` enables `tags: ["autodocs"]` globally, so every component gets
   a docs page. Keep `argTypes` meaningful for controls.

Naming conventions:

- `UI/Button`, `UI/Select`, `UI/Dialog` — primitives from `src/components/ui`.
- `Shared/CopyInline`, `Shared/PageHeader` — `src/components/shared`.
- `Layout/Sidebar`, `Layout/TopBar` — `src/components/layout`.
- `Components/Device/DeviceRow`, `Components/Device/DeviceDetailsCard` —
  feature components (`Components/<Area>/<Name>`).
- `Components/NetworkAccessCard` — top-level cards in `src/components`.
- `Access/…`, `Network/…`, `Routes/…`, `Topology/…`, `Invites/…` — area groups.
- `Pages/Networks`, `Pages/DeviceDetail`, `Pages/Activity`, … — full pages.

Every story is expected to render at 1440 and 390, in light and dark. Stories
that are only meaningful in one language should pass `globals=locale:ru` (or
the toolbar) and document why.

## Fixtures and MSW

Fixtures are typed against the generated OpenAPI model
(`@/api/generated/model`), so an API change breaks `bun run typecheck` instead
of silently producing a broken story. They cover:

- devices of every OS and state (online/offline/updating/push-failed/pending/
  blocked, hub, exit node approved/proposed, long names, empty OS, descriptions,
  tags, credentials) in two networks;
- networks, tags, users, organisation, app config, me;
- access policy (rules, summary, policy versions), subjects, compiled ACL;
- network routes/reports, device routes, peers, MagicDNS names, invites, audit
  activity, topology (nodes/links/observations/stats), revisions, adoptable
  instances.

`mocks/handlers.ts` answers the real URLs used by the generated hooks
(`src/api/generated/easyplane.ts`). To add an endpoint:

1. Add or extend a fixture in `.storybook/fixtures/`.
2. Add `http.get("/api/…", () => HttpResponse.json(fixture))` **before** the
   catch-all. Handler responses are the *payload*; `apiFetch` adds the
   `{ data, status, headers }` envelope the orval hooks expect.
3. Mutations return plausible success envelopes so a play function or an
   accidental click never reaches a backend.
4. Anything not handled by an `/api/*` handler hits the catch-all, which prints
   `[storybook] Unhandled API request: METHOD /path` and returns 501 — no
   request leaves the browser. Treat that warning as a missing fixture.

`/api/events` is mocked with MSW's SSE handler (`sse`) and stays open with a
single `hello`; the topology page's stream therefore never reconnects and no
real endpoint is contacted.

## A11y

`@storybook/addon-a11y` runs on every story (`parameters.a11y.test = "error"`).
The representative set (buttons, dialogs, selects, device rows, access rules,
topology, every page) was also checked with axe-core at 1440 light. The
remaining violations are in components, not stories: account-menu initials,
copy-value buttons, truncated rule names, sidebar aria-labels, low-contrast
counts on segmented controls, unmanaged topology badges, and the login brand
panel's white/60 text.

## Page caveats

- **Devices / Pending approvals** share `DevicesPage`; the pending variant sets
  `pendingOnly`.
- **Invites** has no standalone route in the app. The `Pages/Invites` story
  mounts `AddDeviceDialog` inside `AppShell`, because invites are created from
  the network header and the setup checklist.
- **Device detail** needs the `<Route>` wrapper described above.
- **Login** is shown inside the shell decorator only for convenience; it is
  normally rendered outside `AppShell`, which the story mirrors.
- Error states that require a failed request (e.g. unknown device → 404) are
  not separate stories: browsers log the expected 404 to the console and the
  “every story has no console errors” invariant is more useful. The empty and
  error components have their own stories.
