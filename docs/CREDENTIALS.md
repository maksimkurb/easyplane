# Credential mode: per-device access to an EasyTier network

This document describes mode B (`credentials`) of EasyPlane. Mode A
(`shared_secret`) is the original behaviour and stays the default.

Every claim is labelled:

- **[verified]** — exercised with the real `easytier-core 2.6.4-81487c36`
  built from the pinned commit, in the Phase-1 spike and in
  `test/conformance/credentials.test.ts`.
- **[source]** — read from the pinned upstream sources; not separately
  exercised.
- **[panel]** — our own design/implementation.

## 1. The two modes in one table

| | `shared_secret` (mode A, default) | `credentials` (mode B) |
| --- | --- | --- |
| Who knows the network secret | every device | anchors only |
| How a member joins | the secret itself | a per-device X25519 credential |
| Revoking one device | block it; it still knows the secret | revoke the credential |
| Blast radius of a leaked device | the whole network | that device |
| Extra moving part | none | at least one anchor must be online for **new** members that connect through a rendezvous node |
| Removing an anchor | rotate the secret | rotate the secret (anchors are permanent until then) |

The network page shows this comparison next to the mode switch. New networks
are created in `shared_secret`; switching is an admin action with a dry run.

## 2. Wire-level facts (what the client actually needs)

### 2.1 Member

`NetworkConfig` for a member [verified]:

```text
networkName      = <network>
networkSecret    = <absent>            # the field must be undefined, not ""
secureMode       = { enabled: true, localPrivateKey: <base64 X25519 secret> }
peerUrls, ipv4, hostname, acl, ...     # same as mode A
```

`gen_config` (`easytier-core/src/config/api_input.rs`) treats "no
`network_secret` + `secure_mode.local_private_key`" as a credential instance:
it calls `NetworkIdentity::new_credential(network_name)` (name-only identity)
and passes the private key to secure mode. The client derives the public key
itself; `localPublicKey` is reported back but does not need to be pushed.

A member has no network secret, so it cannot verify a secret-holder's proof.
The client therefore only accepts a peer that proves a **known credential key**
(the anchors publish those) or a connection it dialled itself
(`EncryptedUnauthenticated`, `peer_conn.rs`). A secret holder that dials a
member and is not in the trusted list is rejected with
`authentication failed: invalid proof and unknown credential` [verified — a
"rogue" secret-holder container was refused by a member].

### 2.2 Anchor

`NetworkConfig` for an anchor [verified]:

```text
networkName       = <network>
networkSecret     = <the network secret>
secureMode        = { enabled: true }        # key generated by the client
managedCredentials = [ ManagedCredentialConfig, ... ]
```

```proto
message ManagedCredentialConfig {
  string credential_id = 1;
  string credential_secret = 2;   // base64(32-byte X25519 PRIVATE key)!
  repeated string groups = 3;
  bool allow_relay = 4;
  repeated string allowed_proxy_cidrs = 5;
  int64 expiry_unix = 6;
  optional bool reusable = 7;
}
```

Two facts that shaped the design:

1. **An anchor receives every member's private key.** The protocol has no
   public-key-only form. Anchors are therefore the most trusted devices in the
   network: an anchor can impersonate any member [source + verified].
2. **Anchor configs are not hot-patchable over the config-server channel.**
   `WebClientService` has no `PatchConfig`; `RunNetworkInstance` replaces the
   instance (stop + start). Every credential issue/revoke/renew repushes the
   anchors and restarts their EasyTier instance for a moment [source:
   `management/full/process_rpc.rs`; observed as the anchor's peer sessions
   dropping and reconnecting]. That is why the default TTL is long and
   renewals are batched per network.

An anchor must also be in secure mode: the member's Noise handshake (packet
type 13) is only accepted by a secure-mode peer. A non-secure anchor answers
`unexpected packet type during handshake: 13` [verified in the spike].

### 2.3 Key format and server-side generation

`credential_secret` is `base64` of the raw 32-byte X25519 private scalar
(`credential_manager.rs`: `StaticSecret::from(private_bytes)`); the trusted
entry carries `PublicKey::from(&private)`.

The panel generates credentials with `node:crypto` only: 32 random bytes
wrapped in the fixed PKCS#8 X25519 envelope (`302e020100300506032b656e04220420`)
and `createPublicKey`. Node and `x25519-dalek` clamp identically, so the
derived public key is the one the client uses [verified: a member presenting a
Node-generated key was accepted by an anchor that received the same secret;
the RFC 7748 public-key vector is a unit test].

### 2.4 Trust publication (why the rendezvous node works)

- The anchor publishes every active credential as
  `TrustedCredentialPubkeyProof` in its OSPF `RoutePeerInfo`, HMAC-SHA256
  signed with the **network secret** (`peer_rpc.rs`:
  `HMAC(secret, b"easytier credential proof" || credential_bytes)`)
  [source].
- Anchors verify those proofs with the secret. A peer with an unknown
  `noise_static_pubkey` is disconnected on the next refresh
  (`peer_ospf_route.rs`: "removing untrusted peer from route info") [source +
  verified: the anchor and the node logged exactly that].
- A public/rendezvous node does **not** know the network secret, so
  `credential_proof_is_valid` accepts proofs without verifying the HMAC there
  (`unwrap_or(true)`) [source]. Its trust root is the secret-verified anchor:
  a foreign-network entry is created by a peer that proved the node's secret,
  and a credential peer is admitted only if the entry already exists **and**
  its public key is in the OSPF-propagated trusted set
  (`foreign_network/mod.rs`) [verified in the spike and in conformance].
- Consequence: **one anchor must be online for a credential member to
  (re)connect through a rendezvous node.** Existing sessions survive longer
  (see §3.5).

## 3. Spike results (real easytier-core, pinned commit)

Topology: two isolated Docker networks with a stock public node between them
(private mode, secure mode, relay enabled so data can cross), one anchor and
two members, TOML configs written by hand. Every number below was measured,
not inferred.

### 3.1 Configuring an anchor and a member — works as in §2

- Anchor: secret + `managed_credentials[]` + `secure_mode.enabled`.
- Member: no secret + `secure_mode.local_private_key` (and, for a file-based
  config, `local_public_key`; the config-server path fills it).
- **Key compatibility: yes** — Node-generated 32-byte secrets are accepted.
  The secret is the X25519 private key; the public key is what the anchor
  publishes.
- The anchor's `managed_credentials` needs the **private** key, not the public
  one.

### 3.2 Member joins directly and through the rendezvous node

- Direct (same LAN): member ↔ anchor, `ping` over the overlay, 0 % loss.
- Through the node (disjoint networks, relay on): member ↔ other member and
  member ↔ the far anchor, `ping` 0 % loss. With relay off, data does not
  cross (same as mode A), but discovery/admission still works.
- The node's log shows the anchor admitted as `Admin` (secret-verified) and
  the members as `Credential` (`secure_auth_level:
  EncryptedUnauthenticated`) [verified].

### 3.3 Revoke = remove from every anchor's `managed_credentials` + repush

- The anchor whose list changed rejects *new* connections within ~1 s
  (`authentication failed: invalid proof and unknown credential` in its log)
  [verified].
- An established relayed session kept working for **98 s** in one run (the
  node removed the untrusted peer only on its next OSPF/GC pass) [verified].
  A member that reconnects after the revoke is refused immediately [verified].
- Revocation is only complete when **every** anchor drops the key. In a
  two-anchor run, removing it from one anchor left the other (and the node,
  which still learned it from the other anchor) trusting the device.
- In EasyPlane a revoke also blocks the device, so its own instance is deleted
  and its heartbeat is refused; re-approving issues a fresh key.

### 3.4 Expiry

- The node dropped the live credential peer at `expiry_unix + 0.7 s`, and
  overlay data stopped ~12 s later (route withdrawal) [verified].
- Anchors reject the key at expiry too (their 1 s GC filters expired entries).
- An expired credential is not usable for a reconnect [verified].

### 3.5 All anchors offline

- Existing member ↔ member traffic (direct and relayed) kept working for about
  **100 s**, then stopped: route entries expire without an anchor to refresh
  them [verified].
- A new member (or a restarted one) could **not** connect through the node:
  the node rejected it with `private mode is turned on, foreign network secret
  mismatch` once the foreign-network entry was gone (no secret-verified peer
  left). Even with the entry still alive, a credential published after the
  anchor went away is unknown, so it is rejected the same way [verified].
- Recovery is automatic: when an anchor reconnects, it re-establishes the
  entry, the panel repushes it with the current credential list (the push
  compiler compares managed credentials, so an unchanged revision number is
  enough), and members rejoin [verified in conformance].
- Practical rule: **two always-on anchors** if you rely on the node. The panel
  warns at zero and at one anchor.

### 3.6 Secret rotation

- Full rotation (all anchors + the node) with unchanged members: members keep
  working, credentials stay valid, anchors re-sign the proofs with the new
  secret [verified].
- Partial rotation (anchors rotated, node kept the old secret): the node
  rejects the anchors (`private mode is turned on, foreign network secret
  mismatch`); existing relayed sessions linger until the entry disappears
  [verified]. Rotate the node secret in the same maintenance window.
- Members never verify proofs, so they do not need to be touched for a
  rotation. Their credentials do not become invalid.

### 3.7 What the spike disproved / could not do

- A member cannot be admitted by a rendezvous node without an anchor that
  established the network there (§2.4). This is upstream behaviour, not a
  panel bug.
- There is no way to update `managed_credentials` without restarting the
  anchor instance over the config-server channel.
- A removed anchor still knows the secret and can still be admitted by anchors
  that share it. It cannot dial a member directly (members reject unknown
  secret holders) [verified], but it can accept members that still dial it.
  Remove its endpoints from the network peer list and rotate the secret.

## 4. Panel design

### 4.1 Data model

- `networks.access_mode` — `shared_secret` (default) | `credentials`.
- `devices.role` — `anchor` | `member`. In `shared_secret` mode every device is
  effectively an anchor; the panel reports `effectiveRole`.
- `invites.role` — role a newly enrolled device gets. The first device of a
  credentials network must be an anchor (enforced on invite creation *and*
  approval).
- `credentials` — one row per device:
  `credential_id`, `secret_ciphertext` (AES-256-GCM, exactly like a network
  secret), `public_key`, `groups` (our `tag:*` names, EasyTier ACL groups),
  `allow_relay`, `allowed_proxy_cidrs`, `reusable`, `expiry`, `status`
  (`active|revoked|expired`), `revoked_at/by`, `revocation_reason`.
  The plaintext key is never logged, audited, returned by an API or written to
  a revision row.

### 4.2 Compiler

`PushService` resolves the network and the device's effective role at push
time (network state, like peer URLs, routes and MagicDNS):

- **anchor**: network secret + `managed_credentials` for every active,
  unexpired credential of the network, sorted by id, plus `secure_mode.enabled`;
- **member**: no network secret + its own credential key in `secure_mode`;
- **shared-secret mode**: unchanged.

`configMatchesDesired` now also compares:

- the network secret as `(value ?? "")` (a member's absent secret vs a stale
  secret),
- the member's derived public key (`secureMode.localPublicKey` reported by the
  client),
- every `managed_credentials` entry (id, secret, groups, relay, proxy CIDRs,
  expiry, reusable).

This is what makes revoke/renew converge even when the revision number did not
change: the reconcile loop detects the drift and repushes.

### 4.3 Lifecycle

- **issue** on approval of a member (and on unblock);
- **renew** before expiry (`EASYPLANE_CREDENTIAL_TTL_DAYS`, default 90;
  `EASYPLANE_CREDENTIAL_RENEW_BEFORE_DAYS`, default 14), batched per network,
  idempotent, audited (`credential.renewed`);
- **revoke** on a one-click member revoke, on block/delete of a member, and on
  a mode switch back to shared secret;
- repush: credential issue/renew/revoke repushes **all anchors**; a reissued
  key also repushes that member; every change is audited and published as an
  SSE `network.updated` event.

### 4.4 API

| endpoint | role | purpose |
| --- | --- | --- |
| `POST /api/networks/:id/access-mode/preview` | admin | dry run: anchors/members, secret movement, revoked credentials, warnings |
| `POST /api/networks/:id/access-mode` | admin | apply the migration (reverse requires `acknowledge`) |
| `PUT /api/devices/:id/role` | admin | anchor ↔ member; demotion requires `acknowledge` and returns `needsSecretRotation` |
| `POST /api/devices/:id/credential/renew` | admin | reissue the key now |
| `POST /api/devices/:id/credential/revoke` | admin | revoke + block the device |
| `POST /api/networks/:id/secret/rotate` | admin | rotate; reports `credentialsSurvive` and a rendezvous note |
| `POST/DELETE /api/devices/:id/block|...` | admin/member | anchors require `acknowledgeAnchorRisk: true` in the body (audited) |

Invites carry `role`. Device DTOs expose `role`, `effectiveRole`,
`knowsSecret`, `accessMode` and the device's own credential (public data only).

### 4.5 Add-device UX

The invite dialog asks **"What kind of device is this?"** when the network uses
credentials:

- *Anchor (always-on node)* — holds the network secret; publishes the trusted
  list. Recommended: a server/VPS, two of them.
- *Regular device* — joins with its own revocable credential.

The first device must be an anchor; the API rejects a member invite/approval
and the UI explains why. Device rows show an Anchor/Member badge, the
credential expiry and "knows the network secret". Anchor removal opens a
blocking dialog: rotate the secret (guided, shows the new secret once) or
"remove anyway" with an explicit acknowledgement that is audited.

## 5. Procedures

### 5.1 Enable credentials on an existing network

1. Open the network page → **Device authentication** → switch.
2. Select the anchors (default: hubs/advertised nodes). Preview the dry run.
3. Apply. Selected devices keep the secret; all others get a new credential.
4. Verify at least one anchor is online (the card warns otherwise).

### 5.2 Add devices

- Anchor: create an anchor invite, connect the node, approve.
- Member: create a member invite, connect, approve — the credential is issued
  automatically and pushed to the anchors.

### 5.3 Revoke a member

**Devices → Revoke access** (or the credential card on the device page).
The credential is revoked, anchors are repushed and the device is blocked and
disconnected. Re-approving issues a new key. The node/anchor drop a live
relayed session within seconds to ~2 minutes (§3.3); the device cannot
reconnect at all.

### 5.4 Promote / demote

- Member → anchor: the device starts receiving the secret **permanently**; its
  credential is revoked. Confirm in the dialog.
- Anchor → member: requires an acknowledgement and returns
  `needsSecretRotation: true`. Rotate the secret next; until then the device
  can still join anchors that use the old secret.

### 5.5 Remove an anchor

1. Prefer: rotate the secret first, then delete the device.
2. Or delete/block with "remove anyway"; the panel removes its endpoints from
   the peer list, but the device still knows the old secret.
3. If the network uses the bundled rendezvous node, rotate the node's secret
   in the same window (`RENDEZVOUS_NETWORK_SECRET` + restart) and update
   `EASYPLANE_RENDEZVOUS_SECRET`.

### 5.6 Switch back to a shared secret

Every device gets the secret again (largest blast radius). All credentials are
revoked, but already-deployed keys cannot be recalled; devices you removed
earlier can join again until the secret is rotated. The UI requires an explicit
acknowledgement.

## 6. Honest limits

- **Anchors are super-devices.** They hold every member's private key and can
  impersonate any member. They are also permanent secret holders: removal
  without rotation is cosmetic.
- **A member that is offline at the moment of a key rotation** keeps working:
  its key does not change. A member whose credential was *revoked* and
  reissued while offline converges on reconnect because its own config is
  repushed when it comes back.
- **No anchor online means no new member joins through the node.** Existing
  sessions survive about 1.5–2 minutes; the panel warns, but it cannot fix the
  upstream admission rule.
- **Revocation of a live relayed session is not instant** (up to ~2 min in the
  spike; anchors and expiry are faster). Do not promise "cut off in a second"
  for sessions that go through a node.
- **Every credential change restarts the anchors** for a moment (full
  `RunNetworkInstance`). Batch changes, keep the TTL long, and expect a short
  blip on revoke.
- **Credential groups are EasyTier group names without a group proof.** The
  anchor's trusted entry adds the member's groups to its OSPF peer info, so
  `source_groups` ACL rules match, but this is not the HMAC group-proof
  mechanism we use for `tag:` devices in strict mode. [source for the group
  injection; not separately conformance-tested.]
- **One secret per rendezvous node.** A credentials network on the bundled node
  still needs the node's secret; rotate both together.
- **Import does not adopt credential configs.** The private key in such a
  config is a device identity, not a network; adopting it would either break
  the chain or open the network. The import error now explains how to do it
  properly (create the network, add the device as a member, use the issued
  credential).
- **Members never learn the relay/proxy grant from the panel at runtime**:
  `allow_relay` and `allowed_proxy_cidrs` are enforced by the anchors' trusted
  entries [source], not by the member's own config.

## 7. Tests

- Unit: key derivation (RFC 7748), compiler determinism, managed-list drift
  (revoke/renew/grant), member vs anchor configs, effective role, group mapping
  and expiry.
- Integration (real PostgreSQL): invite roles, first-anchor rule, migration
  preview/apply, member credential issuance, admin-only role/revoke,
  revoke→block→re-approve, demote acknowledgement, rotation and the reverse
  migration.
- Conformance (real pinned clients): a member joins through the rendezvous
  node while an anchor is online; with the only anchor stopped, a new member is
  refused by the node and recovers when the anchor returns; revoking the member
  deletes its instance, blocks it, and traffic stops.
- Web: the access-mode card (both modes, en/ru) and the role badges.

## 8. Open questions

- Can anchors hot-patch `managed_credentials` through the instance RPC portal
  (`CredentialManageRpc`)? It is a separate channel we do not drive; if a
  future control-plane transport reaches it, revoke/renew would stop restarting
  anchors.
- Should a member's own instance stop immediately on an SSE-style control
  message? Today the panel deletes the instance on revoke/block; a member that
  is only expired keeps running until its next reconnect, and the anchors drop
  it.
- Would a per-member expiry of hours (instead of 90 days) be useful for
  high-churn fleets? It would restart anchors more often; not recommended.
